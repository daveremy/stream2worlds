          The experiment

          Can any stream become a world in minutes?

          Every organization already describes itself in streams: orders, shipments, tickets, sensor readings, database writes, audit logs. Almost nobody reads them as a whole, because turning them into a model of the business has always meant a schema project, an integration project and a data team. Stream2Worlds tests whether that step can be skipped.

          Point it at a stream it has never seen. System 1, fast and cheap, runs on every event. System 2, slow and deliberate, reads the world System 1 produces, repairs what it can, and teaches System 1 what it learned. Within minutes, with nothing configured, you should see three things:

          Understanding

          A world of entities and relationships, typed and named, built from whatever the stream contains. The stream's mess is repaired in the open, and every repair can be undone.

          Prediction

          Forecasts with probabilities, shown as possible worlds. Every forecast is scored against what actually happens, so every predictor carries a public track record.

          A possible world here is a sampled future of the world: one future state of the entity graph, rolled forward from the current snapshot. A forecast is a predicate evaluated over those samples, with Monte Carlo semantics in the style of MCDB, recorded before the outcome and graded after. In probabilistic databases the phrase means uncertainty about the present; on this page it always means the future.

          Action

          Rules that fire on the actual world or on any likely one, and act through plugins. If this, then that, across worlds.

          What would count as success

          The claim under test is narrower than the vision: that System 2 makes an unfamiliar stream useful faster than heuristics alone, and that forecasts can earn trust through a graded record. Targets rewritten after the critic pass; none measured yet.

          < 5 minfrom first event to readable evidence: samples, shapes, candidate entities
          < 30 minto a verified answer to a predefined operational question, failures reported
          accuracy, not namesidentity, relationship and state accuracy against owner labels; false merges and abstentions reported apart
          correction minutestotal human time to reach target accuracy, not inbox clicks
          Brier skill > 0against base rate and a simple contextual baseline, with sample counts and intervals
          bounded p99 lagunder a declared workload, with memory and disk growth; System 2 spend capped, backlog reported

          And the one that matters: does someone make a better decision, or save real work, compared with how they do it today?

          Zero-effort setup

          Your coding agent sets it up in a minute

          The real first touch will not be a person reading docs. It will be someone at a company, coding agent in hand, typing "set up s2w on our orders topic". The agent finds the stream, connects it, and hands back a live world and an MCP connection to it. Nothing to provision, nothing to configure, and nothing sensitive leaves the machine without the user seeing it first. This gets designed first, not bolted on before launch.

          Built for agents to drive

          Every command is non-interactive, idempotent, and has a --json mode. Errors say what to try next. An llms.txt, an AGENTS.md snippet and a Claude Code skill teach the flow, so any coding agent can run it without a human reading the docs.

          Reuse what already works

          s2w doctor names the exact missing piece (unreachable host, ACL denied, no registry credentials) and the one command a human needs to run. It reuses the client config and auth the user already has rather than hunting for secrets, which would trip security tooling. The universal escape hatch: if you can consume the topic with any tool, s2w reads it, as in kcat -C … | s2w watch -.

          Local by default, cloud by manifest

          Company topics run locally unless someone chooses to share. Sharing binds to an export manifest the user approves (topic, fields, transformations, destination, retention, model provider) and the connector enforces it on every event, quarantining unexpected fields. The connector sends outbound over HTTPS: no inbound ports, no VPN.

          No signup to start

          Local mode needs no account at all. For public streams, or an approved share, a temporary cloud workspace comes back as a URL. Claiming it needs a login and a separate credential, so possessing the URL is never enough.

          Safe by default

          No consumer group: s2w assigns partitions, seeks by timestamp and never commits, so it needs only topic READ and fires no lag alerts. A bounded lookback, bandwidth limits and a sample cap protect the broker. Sharing uses field allowlists and keyed pseudonyms, described as pseudonymization, not anonymity. The client agent can act as System 2 itself, so data reaches only a model provider the company already approved.

          Local-first for the open-source crowd

          s2w up --local does everything on the machine, with the UI on localhost and System 2 on any model the user configures. The cloud adds a hosted world, System 2 on our budget, and a share link. Same binary, same world format.

          What must work for the magic to hold: JSON, Avro and Protobuf through a registry, and SCRAM, mTLS, MSK IAM and Confluent API keys. Kafka first. Postgres WAL needs a replication slot, which can retain disk on the source if it stalls, so the agent path prefers an existing Debezium topic, and a direct WAL connection stays a deliberate, human-approved step.

          Why this could matter

          An organization is its streams

          Much of what changes in an organization shows up in its streams. A system that can read them could show an organization to itself, live: few-shot, with no per-event model charge, from any stream, in minutes. Not everything lives in streams (contracts, rates and policies sit in tables and documents, which is what side sources are for), and the first slice tests a much smaller piece of this vision.

          See the business as it is right now

          A live world instead of yesterday's dashboard. Scrub it backwards to the exact event that changed something, because the world is a replay of the log.

          See what is probably coming

          Forecasts with a published calibration record, shown as possible worlds. Trust in a predictor is earned from its record rather than asserted.

          Act before it happens

          Rules on worlds, through action plugins. Act on what happened, or on what is 80% likely to happen, with guard rails that tighten as the stakes rise.

          Start without the integration project

          No schema, mapping or event catalog to write first. System 2 proposes the model, and the mapping builds up from your answers in the inbox.

          Know what it knew

          Every repair, inference, forecast and action is an event with its source and confidence. You can replay what the system knew when it acted, and separately what it believes now.

          Could work for anyone with streams

          A retailer's orders, a city's 311 calls and transit feeds, a utility's grid sensors, an airline's operations. The first tests use public streams.

          The cloud path, and the enterprise version of it

          The default path is the agent-driven setup above: an outbound connector and a temporary cloud workspace. For a company that wants more than a trial, setup should still take minutes; a customer's security review sets the real timeline. A hosted instance joins the customer's network over Tailscale, so it can read an internal stream without opening an inbound port, and their security team can scope and revoke what it reaches. Tailscale limits reach; it does not keep data inside their network. Where data cannot leave, the same Rust binary runs on their hardware, with System 2 pointed at a local or approved model.

          Why now

          Decision models make System 1 possible

          PredictStream hit a wall that no amount of engineering could fix: understanding an event meant calling an LLM, and an LLM takes seconds and costs money per event. The alternatives were fast but blind: rules someone had to write, or classical models trained per stream on labels nobody had. You could have speed or semantics, not both.

          A new class of model changes that trade. Decision models such as TypeSafe's Jev take natural language and application state and return typed judgments with probabilities, built to be called like a function rather than chatted with. If they deliver on that at stream speed and stream cost, semantic understanding moves into the hot path for the first time. That is System 1, and it is the piece PredictStream was missing. Around it, the other pieces have also arrived: LLMs good enough to propose a domain model from a sample (System 2, amortized across millions of events), MCP as a standard way for agents to consume a world, and a Rust ecosystem that makes a single fast binary practical.

          What a decision model does in S2W

          The per-event judgments rules cannot make and LLMs are too slow for: which entity this event is about when ids are missing, what kind of event a free-text log line is, whether this change looks like the start of an abandonment, whether two records are the same customer. Each one is a typed question with a probability, logged as an event, so it can be graded and replayed.

          In theory, so measured in practice

          Nobody has measured Jev's latency, cost or accuracy on these questions yet, and more models of this kind are coming fast. That is why System 1 is a seam with a built-in bake-off. If decision models deliver, S2W feels like magic. If they do not yet, rules and embeddings still carry it, just less impressively, and the scorecard shows exactly when a new model crosses the line.

          The dashboard

          Seeing possible worlds

          Agents will do most of the reading, but people decide whether to trust the thing, and people trust what they can see. Visualizing forecasts is its own design problem: show the future without pretending to know it, stay readable with hundreds of forecasts, and make the moment reality arrives feel like something. One grammar runs through all of it: solid is what happened, dashed ochre is what might, weight and opacity carry probability, and dash patterns back up colour so nothing depends on colour alone.

          The collapse is the signature moment

          When reality arrives, the ghost turns solid (confirmed) or shatters (refuted), and the cone snaps to the line. A confident forecast that reality contradicts flashes as a surprise. That animation is what people will remember and clip.

          Diff two worlds

          Pick a possible world and see it onion-skinned over the actual one: which entities change state, which links appear, what it would cost. The same diff is what an agent gets from explain.

          Native views per domain

          On a map, a forecast arrival is a dashed arc ending in a time-window ellipse; for state machines, a flow diagram shows how many carts are forecast to reach checkout versus abandonment, with bands.

          Level of detail, always

          Zoomed out: heat and counts. Zoomed in: ghosts, cones and evidence. No branch is ever drawn without its forecast record one click away: probability, predictor, track record.

          The design

          Seven decisions that make it work

          PredictStream was a pipeline of phases: ingest, identify, predict, act. Identify mattered most, and the LLM agents in it were too slow for a stream. These decisions keep what worked and remove what didn't.

          System 1 and System 2

          System 1 runs on every event in microseconds to milliseconds: rules, embeddings, small decision models. System 2 runs asynchronously in seconds: LLMs reading world snapshots and gaps. System 2 never sits in the stream. It teaches System 1 by writing proposals (types, repairs, predictors) into the log, where accepted ones compile into System 1's configuration.

          Any stream, repaired in the open

          Real streams have no event types, drifting field names, missing ids, duplicates and gaps. The raw stream is never edited. Repairs are events with a confidence and a source, and the world folds over raw events plus repairs, so a wrong repair is revoked and the world re-projects. Proposals stay inert until accepted, and low-confidence repairs live in a preview world that rules cannot act on.

          The world is the product

          A world is a projection folded over the log: entities, relationships, current state. Time travel is replaying to an offset. A model change (a new entity type, say) re-projects history, which is why the mockup's graph tidies itself at #0016. So there are two replays: the world as known then, and the world as reinterpreted now. A later repair changes the second, never the evidence behind a forecast already issued.

          A prediction is a fork

          A fork is the base world at t plus a suffix of predicted events, each with a probability. Forks can fork. Beam width, a depth limit and a probability floor keep the view readable. Rules read forecasts, not branches: a forecast is a bounded question ("shipment exception within 24h") with one probability, so splitting a branch or changing the beam never changes an action.

          Terms: rollout is the mechanism that produces futures from the base world; one fork is a sampled future world; the set of forks open at an offset is the world ensemble (never "ensemble" alone, which in machine learning means model averaging).

          Every forecast gets graded

          A forecast is an immutable record: target, entity, issue time, horizon, probability, predictor version, evidence cutoff. Its outcome is scored apart from its display. Pruning hides a branch but never un-scores it, and an outcome the stream cannot observe is censored, not refuted. This is the feedback loop PredictStream never had, and it ranks System 1 engines on the same questions.

          If this, then that, on worlds

          One rule primitive: a condition over the raw stream, the actual world, or a registered forecast, plus an action plugin. An action does not care whether its trigger happened or was predicted; the guard rails do.

          Silence is ambiguous, and that is useful

          When a predicted event never arrives, either the world changed or the stream dropped it. Same signal, two readings. You pick one in the inbox, and the answer teaches the system which kind of silence it was.

          Rules and actions

          If this, then that, across worlds

          Subscriptions grow into rules. A rule's condition reads the actual world or a registered forecast (a bounded question with a horizon), never a branch. Its action is a plugin. The sketch below is illustrative syntax, not a decided language.

          rule "stalled order"
  when actual: Order.status == "paid" and no OrderShipped within 48h
  then slack("#fulfilment", "{order} paid {age} ago, not shipped")

rule "save the cart"
  when forecast(Cart.abandoned within 30m) >= 0.70
  then email.winback(cart.customer)            # dry-run, with a holdout

rule "delivery risk rising"
  when forecast(Order.delivery_exception within 24h) rises by > 0.20 within 10m
  then page(oncall, evidence = world.diff)

          Action plugins

          Webhook, Slack, email, ticketing, HTTP, and user code as WebAssembly plugins, so a customer can add an action without touching the core. The host enforces each plugin's egress, secrets and limits; nothing is trusted from the plugin's own declaration.

          Guard rails

          Rules act only on accepted state, never on provisional repairs. Acting on a forecast is opt-in per rule. New rules start in dry-run. Irreversible actions (payments, deletions, messages to customers) need approval. Every action logs the world, forecast and offsets that triggered it, and every rule has a rate limit.

          Acting changes the outcome

          If a win-back email goes out and the customer returns, nobody knows whether the email caused it, and a prevented abandonment makes a good forecast look wrong. So the first experiment is observational. Later, acted-on forecasts need a randomized holdout, and promotion to automation depends on measured action outcomes, not forecast accuracy.

          Stream text is untrusted

          A ticket or log line can try to steer System 2 into a bad mapping or rule. Model workers hold no action credentials, proposals use a constrained format validated before acceptance, and revoking a repair invalidates the actions that depended on it.

          LLMs as clients

          The real users will be agents

          The inbox and the demo UI matter, but most of the reading will be done by LLMs. That suits the design: the world is already a compression of the stream (an agent wants a 2,000-token situation report, not ten million events), and the rule language is the kind of small, checkable language LLMs write well. The UI becomes the place people see what agents saw, did and proposed.

          One language for reading, watching and acting

          A query is a when with no then. A subscription is a rule whose then is "notify me". An agent learns one small grammar, and a person can read every line it wrote.

          A compiler loop for rules

          The agent writes a rule, gets precise errors, sees a backtest ("would have fired 14 times last week; here are 3"), and revises. Constrained language with fast feedback is far safer than an agent writing code against the stream.

          Agents get woken, not just polled

          then wake(agent: "ops", with: evidence) is an action plugin. The agent arrives holding the world diff, the forecast and its evidence, instead of starting cold.

          Every agent is an identity in the log

          Its reads, proposals and actions are events. MCP starts read-only; any write capability is granted explicitly and scoped to a task, and a good record never expands an agent's powers on its own. Stream content comes back as quoted data, but the real risk is a coding agent that reads poisoned evidence while holding shell or deploy tools, so investigation and execution stay separate.

          Architecture

          Two systems over one log

          Sources, repairs, System 2 proposals, predictions and verdicts all land in the same log with offsets. Everything downstream is a projection of it.

          Implementation

          Rust from day one, with System 1 as a plug-in

          Rust because the core has to be fast, small and easy to drop into someone else's network: one static binary, predictable memory, no garbage-collection pauses in the stream, and good async I/O for many sources at once. The earlier prototypes (worldcraft, timely_worlds, strema) are already Rust, and Feldera's DBSP engine, the incremental option for later, is a Rust crate too. The browser view is the one part that is not Rust; the binary serves it.

          System 1 is about to get crowded. Jev and a wave of other small decision models are arriving fast, and this month's best engine will not be next year's. So nothing in the core depends on one. The sketch below shows the seams we expect; each one ships with two real implementations in the first slice (see Continuous architecture), so every trait is designed against two cases, not guessed from one.

          /// A fast judgment: typed question in, typed answer with a probability out.
pub trait System1: Send + Sync {
    fn profile(&self) -> EngineProfile;          // latency budget, batch size, cost per call
    fn judge(&self, q: &Judgment, view: &WorldView)
        -> Result<Verdict, Abstain>;                // abstaining is a first-class answer
}   // deadlines live in the shell; verdicts are logged as events, so replay never re-runs an engine

/* eventual seams, not first-slice code */
}

/// Slow, asynchronous reasoning over snapshots. Never called per event.
#[async_trait]
pub trait System2: Send + Sync {
    async fn propose(&self, snap: &Snapshot, gaps: &[Gap], budget: Budget) -> Vec<Proposal>;
}

pub trait Source    { fn open(&self, from: SourceCursor) -> BoxStream<'static, RawEvent>; }
pub trait Predictor { fn fork(&self, world: &WorldView, at: Offset) -> Vec<ForkSpec>; }
#[async_trait]
pub trait Action    { fn policy(&self) -> ActionPolicy; async fn run(&self, t: &Trigger) -> ActionResult; }
                    // policy is enforced by the host: egress, secrets, approval tier

pub enum Origin { Source(SourceId), Repair(RepairId), System2, Predictor, Verdict, Action }

pub struct Issuance {                           // immutable once written
    pub question: QuestionId, pub entity: EntityId, pub issued: Offset, pub horizon: Duration,
    pub p: f32, pub predictor: Version, pub evidence_cutoff: Offset,
}
pub struct OutcomeObservation {                 // appended later, versioned; never edits the issuance
    pub issuance: IssuanceId, pub outcome: Outcome, // Positive | Negative | Censored
    pub observed: Offset, pub source: SourceId,
}

pub struct Fork {                               // display: a forecast drawn as a world
    pub id: ForkId, pub parent: Branch, pub at: Offset,
    pub suffix: Vec<(Event, f32)>,            // only what this world adds
    pub issuance: IssuanceId, pub shown: bool, // pruning hides; it never un-scores
}

          A router, later

          Once there are engines to route between, each judgment names a latency budget. The router picks the engine that fits: a rule if one exists, then embeddings, then a decision model such as Jev, falling back to System 2 later if nothing is confident.

          A built-in bake-off

          Forecasts get graded, so engines do too. Run two System 1 engines in shadow mode on the same eligible questions and the scorecard ranks them on accuracy, abstention, latency and cost. When a better model ships, you swap it in on evidence.

          First-slice workspace, kept small. Adapters depend only on s2w-model, never on the core or on each other.

          Continuous architecture

          Pay architecture down every week, not every other sprint

          The usual burden builds up because architecture is treated as a phase: build fast, then schedule a cleanup that loses to the next demo. Alternating sprints has the same flaw at a smaller scale, since debt compounds for a sprint and then cleanup becomes a project. The proposal instead: make the architecture executable so drift fails a build, pay a fixed share in every sprint, and keep a circuit breaker for when debt gets ahead anyway.

          A functional core, an imperative shell

          The heart of S2W is pure: events in, world out, forecasts graded, with no async and no I/O. Time, randomness, accepted mappings and external results are passed in as inputs, and clippy bans wall clocks, HashMap iteration order and RNGs in the core. A simple reference fold stays forever as the oracle for any faster implementation.

          Layers enforced by the build

          The workspace is the architecture: s2w-core and s2w-model do no I/O, adapters depend only on the model, and the app composes them. A CI check holds a per-crate allowlist of dependencies. An allowlist, not a denylist, because agents add crates nobody thought to ban.

          Every seam gets two implementations, early

          An abstraction designed against one case is a guess. So each seam we keep ships with two real implementations in the first slice, chosen to differ where it hurts (see the table). A seam that cannot find a second use in the slice stays a plain module until it can.

          Measure how hard change is

          Track how long representative changes take, how many unrelated modules they touch, and which defects recur. Removing a feature or an obligation counts as progress; shrinking line counts is only a symptom.

          Built mostly by agents, so guard against agent drift

          Coding agents duplicate types across issues, widen visibility to make tests compile, reach for unwrap and #[allow], and regenerate a golden hash when it breaks. Countermeasures: shared types live only in s2w-model; an AGENTS.md in each crate states its allowed dependencies and invariants; lints for unreachable_pub and reasonless allows; golden files owned by a human, so any hash change needs sign-off. An LLM architecture reviewer is advisory; the mechanical checks are the gate.

          Cadence

          • Every PR: the mechanical checks gate it; an architecture-lens reviewer adds advisory notes against the decision records.
          • Every sprint: about a quarter of capacity is held in reserve for architecture. It is a reserve, not a quota: correctness work belongs in each feature's definition of done, and some weeks need nothing extra.
          • Every fourth sprint: a fresh-eyes review over actual changes and failures, asking "if we started today, what would we build differently?" "Delete this" and "change nothing" are valid answers.
          • Circuit breakers: a broken replay invariant, unbounded growth, the same boundary crossed by repeated changes, or change times rising sprint over sprint. Any of these earns a focused architecture sprint. Debt items name their observed cost and the next task they will slow.
          • Decision records: short, numbered, in the repo, and summarised in each crate's AGENTS.md so the agents doing the work actually read them. Persisted formats get versioning and migrations before any Rust API is frozen.

          A comparison

          Stream worlds and AI world models

          They are different animals solving the same problem, and the comparison runs both ways. The PredictStream intuition was that a stream is to an organization what vision is to a person: a constant flow of observations from which you keep an updating picture of reality and imagine what comes next. AI world models make that move for physical environments. Genie 3 generates playable worlds, NVIDIA's Cosmos trains world models for robots and cars, V-JEPA predicts in an abstract state space, and Dreamer-style agents plan by imagining futures. That is why the field reads as gaming: its showcase outputs are rendered worlds.

          What S2W can borrow

          Forecast in the abstract state (entity changes), not raw payloads, as JEPA argues. Try candidate actions in imagined worlds before taking them, as Dreamer does, once the intervention problem is handled. And eventually learn dynamics across many streams: a model that has seen many organizations' event flows might forecast a new one zero-shot, the way a video model already knows that dropped things fall.

          What S2W offers back

          A state you can inspect and correct, imagined futures graded in public against reality, and structured context for agents that act inside businesses, where the relevant world is not pixels. An explicit world model is what an agent lacks when it acts on a company.

          Where they might meet: a learned dynamics model over S2W's entity states, a world model of organizations. That is far beyond the first slice, and exactly the kind of idea to hold lightly. In the Hacker News pitch it stays to one line, since reviewers warned the vocabulary invites eye-rolls; here it earns a section.

          Project history

          From "turn on predictions" to a world model

          The EventStore idea. It started at EventStore with a simple wish: you should be able to switch on predictions for an event store the way you switch on a projection, and start getting a stream of predicted events alongside the real ones. The same would work for any database through its write-ahead log.

          PredictStream. The first build was a pipeline of phases (ingest, identify, predict, act), each with pluggable, configurable agents, some LLM-based and some not. Identify mattered most: domain agents guessed what the stream was about and elaborated each event with meaning, which made everything downstream better. Act turned out to matter as much as predict, because you could subscribe to a predicted event (CartAbandoned) exactly as you would to a real one (AddressChanged). The wall was speed: LLM agents in the pipeline were too slow for a stream.

          The insight that came out of it. The most interesting thing identify produced was not an enriched event. It was a model of the world behind the events. A stream is an interleaving of many entities' lives: every cart, customer and order emitting events on its own schedule. Predicting the next event from the raw sequence is like predicting the next word in a room where a hundred conversations overlap: possible, but most of the signal is buried. Untangle the stream into entities with state and relationships, and the question changes from "what comes next in this stream?" to "what does this cart do next, given that it holds three items, has been idle ten minutes, and belongs to a customer who usually buys on the second visit?" That question is smaller, far more data-efficient, explainable, and it can use neighbours: a delayed shipment makes its customer's next support ticket likelier. Next-event prediction gets better because the world model supplies the context the raw sequence hides.

          Many worlds. Once there was a world model, predictions stopped looking like events and started looking like alternative futures of that world. One world is the current best view of reality; each prediction forks another. Streamed longer, joined with other streams, supplemented asynchronously, the world model became the thing that was actually interesting: a projection of reality at a point in time that you could rewind, fast-forward and branch. It was called the many-worlds project for a while. Timely Dataflow looked like the right engine for many projections, but its programming model was hard to work with while the requirements were still being discovered.

          Three Rust prototypes, then S2W. worldcraft, timely_worlds and strema each explored one piece. Stream2Worlds (September 2026) puts them together, with System 1 and System 2 in place of the too-slow pipeline and a visualization-first view in place of an abstraction nobody could picture.

          predictstream Python · several versions · predictstream.ai

          Phased pipeline of pluggable agents. Carries forward domain elaboration and subscribing to predicted events as if they were real.

          worldcraft Rust · Differential Dataflow

          Finds entities and relationships in a raw Kafka stream and keeps a living graph, with human approval. Carries forward discovery heuristics and the approve step.

          timely_worlds Rust · Timely

          Predicted futures as branches over a base world, with beam and depth limits and "true in any scenario" subscriptions. Carries forward the fork idea, now as forecasts drawn as worlds.

          strema Rust

          A world graph built from a token stream, with structural surprise detection. Carries forward surprise as a System 1 signal and the "externalize the world model" framing.

          Status: an experiment, held lightly. Open source if it flies. A hobby-slot project under the September life pivot.
