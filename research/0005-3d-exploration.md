## 0. How big is a "world of realistic size"?

### Facts

Measured by the author on 2026-09-27, 09:58–09:59 MST (Sunday morning), 62 s of `https://stream.wikimedia.org/v2/stream/recentchange` (event timestamps spanned 83 s):

| | all wikis | enwiki only |
|---|---|---|
| events | 2,299 (27.7/s) | 283 (3.4/s) |
| distinct titles | 1,490 | 221 |
| distinct users | 440 | 105 |
| event types | categorize 1,140 · edit 941 · new 119 · log 99 | — |
| busiest wikis | commonswiki 739 · enwiki 283 · zhwikisource 276 · wikidatawiki 210 | — |

A third-party figure of "about 50 changes per second" for the same stream appears in an Apache Pinot blog post (search snippet; the page returned 403 on fetch — **UNVERIFIED**) — https://medium.com/apache-pinot-developer-blog/analyzing-wikipedia-in-real-time-with-apache-kafka-and-pinot-4b4e5e36936b. The 30-minute pilot in [research 0004](0004-revert-pilot.md) saw 1,854 eligible human enwiki edits.

### Judgment

Roughly 1,900 new entity ids per minute across all wikis, so about 100,000 entities and a few hundred thousand relationships per hour of the full stream; enwiki alone is a tenth of that. No candidate library draws 100k labelled nodes with edges at 60 fps on a laptop, and no person can read them. **Level of detail is therefore a requirement of the query API, not a rendering trick**: the explorer must be able to ask for the world at a coarse grain (types, clusters, counts) and for entities only near a focus. That is the single most important consequence of this note for #10.

**Scale evidence.** Nobody publishes a "60 fps at N nodes and M edges" figure for a 3D graph; what exists: deck.gl's 1M points (points, no edges); cosmos.gl's "hundreds of thousands" (2D, GPU layout); Ware & Mitchell's 1,000-node graphs read at <10% error (perception, not rendering, §5); for 3d-force-graph, a user report "5,000 nodes and 7,000 links… the performance significantly drops after 7k elements" (open issue, no maintainer reply) — https://github.com/vasturiano/react-force-graph/issues/223 and "1M nodes… it become freezes" — https://github.com/vasturiano/3d-force-graph/issues/668. three.js's own instancing example shows INSTANCED and MERGED at one draw call for 10,000 objects while NAIVE scales linearly — https://github.com/mrdoob/three.js/blob/dev/examples/webgl_instancing_performance.html.

**Embedding without Node at runtime.** memory-serve loads assets from `build.rs` (`load_directory`), and "In release mode text-based files like HTML or javascript are compressed using brotli at compile time and decompressed at startup"; in debug, "files are served dynamically" — https://docs.rs/memory-serve/latest/memory_serve/. Every candidate ships a self-contained dist: `three/build/three.module.js` (663 KB), `three.webgpu.js` (2.28 MB), `3d-force-graph/dist/3d-force-graph.min.js` (1.31 MB, includes three), `@cosmos.gl/graph/dist/index.min.js` (719 KB) — unpkg `?meta` listings, author-verified 2026-09-27. three.js documents plain ESM, import maps and CDN use with no framework — https://threejs.org/docs/#manual/en/introduction/Installation.

### Judgment

**three.js directly, with our own instanced scene graph.** The reasons, in order: every 3D graph library in the table is a thin layer over three.js anyway; the ones that are pleasant (3d-force-graph) draw one mesh per node and stall at low thousands, which the measured stream reaches in two minutes; the one that scales (cosmos.gl) is 2D by design and its commercial twin just went non-commercial again, which is a warning about depending on the wrong package name; deck.gl scales for points but its graph layers are 2D and "semi-maintained"; Babylon is 10× the download for no graph ecosystem; R3F needs React on a page that has no other reason to ship it. An `InstancedMesh` for nodes plus a `LineSegments2` for edges is two draw calls at any count we will show after level-of-detail (§7), and the frame budget then goes to layout and label placement, where it belongs. WebGL2 today; `WebGPURenderer` is one import away when its churn settles, and the fallback is built in.

**Runner-up: 3d-force-graph for the first prototype**, because its 2D twin `force-graph` takes the same `{nodes, links}` contract and the same d3-force-3d engine, so the gate-2 2D graph and the first 3D explorer can share one client data layer. Move off it the day the visible set passes a few thousand objects or labels stop reading. For the gate-2 2D graph itself, `force-graph` (57 KB) or `sigma` (26 KB, scales further, graphology as the client model) are both fine; keep the client data contract in the d3 shape (`id`, `source`, `target`) that all of them accept.

**Licence hygiene.** The `@cosmograph/cosmos` history (MIT for one window, CC-BY-NC on both sides of it) shows npm names can change licence between minors. cargo-deny covers Rust only; the JS bundle needs its own allowlist check (e.g. `license-checker` in the CI job that rebuilds the bundle), pinned by lockfile.

**Delivery.** Commit the built bundle (or vendored ESM files with an import map) under the app crate's asset directory; memory-serve embeds it at compile time, so the Rust build never needs Node. A Node toolchain exists only in the CI job that regenerates the bundle, and a CI check asserts the committed bundle matches the lockfile. The single-binary promise is kept.

## 2. Layout for a graph that changes continuously

### Facts

**What mental-map preservation does and does not buy.** Archambault, Purchase & Pinaud (TVCG 17(4), 2011, DOI 10.1109/TVCG.2010.78; abstract via https://cronfa.swan.ac.uk/Record/cronfa13909): small multiples were significantly faster than animation; animation was more accurate for "what was added in this timeslice"; **preserving the mental map had no meaningful effect on error rate or time** under either presentation. Archambault & Purchase (PacificVis 2012, DOI 10.1109/PacificVis.2012.6183578; abstract via https://api.openalex.org/works/doi:10.1109/PacificVis.2012.6183578): "no significant difference in response error rates when preserving the mental map" for memorability, but **interesting subgraphs that stay visible over time aid memorability**. Archambault & Purchase, GD 2012 "Mental Map Preservation Helps User Orientation in Dynamic Graphs" (https://doi.org/10.1007/978-3-642-36763-2_42; body paywalled) is summarised by GraphDiaries (fetched PDF, below) as "stabilized layouts better support network exploration". Their synthesis, IJHCS 71(11), 2013 (https://doi.org/10.1016/j.ijhcs.2013.08.004; abstract via https://research.monash.edu/en/publications/the-map-in-the-mental-map-experimental-results-in-dynamic-graph-d/): "To date, no experiment has found conclusive evidence that supports the effectiveness of the mental map in the comprehension of a dynamic graph series." Purchase & Samra, Diagrams 2008 (https://doi.org/10.1007/978-3-540-87730-1_9; abstract via https://eprints.gla.ac.uk/35837/): the extremes (high or low preservation) beat the middle setting. Beck, Burch, Diehl & Weiskopf's taxonomy (CGF 36(1), 2017, https://doi.org/10.1111/cgf.12791) splits the field into time-to-time mapping (animation) and time-to-space mapping (timelines); evaluations "emphasize mental map stability or compare animated to timeline approaches".

**Online layout algorithms.** Brandes & Wagner, GD 1997 (https://doi.org/10.1007/3-540-63938-1_66): next layout = maximum posterior of quality × a stability prior on the previous layout, instantiated as a spring embedder with an extra force toward the previous position. Frishman & Tal, TVCG 14(4), 2008 (https://doi.org/10.1109/TVCG.2008.11): online layout with pinning weights that let recently changed nodes and their neighbours move, GPU up to 17× CPU; edge-less new nodes placed on a ring, which produced a visible ring artefact in a later comparison (**secondary**, from Crnovrsanin below). Brandes & Mader, GD 2011 (https://doi.org/10.1007/978-3-642-25878-7_11; Mader's dissertation fetched, https://kops.uni-konstanz.de/bitstreams/118e7eeb-d4f0-4256-9619-9516b812abd0/download): of aggregation, anchoring and linking, "linking is a generally preferable approach", and "anchoring with aggregation as reference and linking provide explicit control over the balance of readability and stability"; linking needs future slices, so **anchoring to the previous layout is the online form**. Xu, Kliger & Hero, DMKD 27, 2013 (https://arxiv.org/abs/1202.6042): a temporal penalty on movement added to MDS/Laplacian layouts, explicitly online. Crnovrsanin, Chu & Ma, JGAA 21(1), 2017 (https://doi.org/10.7155/jgaa.00406; GD 2015 PDF https://vis.cs.ucdavis.edu/papers/tarik_incremental.pdf): incremental FM³ plus an idle-time refinement of high-energy regions; new-node placement: no positioned neighbour → random in the bounding box, one → at edge length from it, ≥2 → their centroid; result "around 1.5 to 5.5 times improvement [in energy] over pinning and 19 to 133 times for aging"; datasets include a live Stack Overflow feed (80 → 638 nodes). Simonetto, Archambault & Kobourov, "Event-Based Dynamic Graph Visualisation", TVCG 26(7), 2020 (https://arxiv.org/abs/1709.00372): DynNoSlice lays out node trajectories in a 2D+time cube with a **mental-map force that caps the angle a trajectory makes with the time axis, i.e. a velocity cap**; on continuous datasets it beat timeslicing (movement 6.57 vs 25.47; crowding 0 vs 6 on Rugby; 3 vs 682 on Pride & Prejudice); it is offline. Arleo, Miksch & Archambault, CGF 41(6), 2022 (https://doi.org/10.1111/cgf.14615) makes it multilevel and "competitive… in running time"; still offline.

**Engineering.** d3-force: `alpha` decays from 1 by `alphaDecay` ≈ 0.0228 (≈300 ticks to `alphaMin`); reheat with `alphaTarget(0.3).restart()`; pin with `fx/fy`; **nodes with NaN positions get a phyllotaxis placement**, so an unseeded new node lands far from its neighbours — https://d3js.org/d3-force/simulation. d3-force-3d adds `z, vz, fz` and `numDimensions(1|2|3)` — https://raw.githubusercontent.com/vasturiano/d3-force-3d/master/README.md. ngraph.forcelayout "monitors graph changes via graph events" and supports `dimensions: 3` and `pinNode()` — https://github.com/anvaka/ngraph.forcelayout. cosmos.gl defaults `simulationDecay` 5000, `simulationFriction` 0.85, `simulationGravity` 0.25 — https://raw.githubusercontent.com/cosmosgl/graph/main/src/config.ts. ForceAtlas2 (Jacomy et al., PLoS ONE 9(6), 2014, https://doi.org/10.1371/journal.pone.0098679) is designed as a continuous layout with no auto-stop, LinLog mode for communities, and per-node adaptive speed from a "swinging" measure. The Gephi streaming format (one JSON object per line, `an|cn|dn` for nodes, `ae|ce|de` for edges, e.g. `{"an":{"123":{"TYPE":"Person:Actor","label":"Tom Hanks",x:333,y:222,…}}}`) is confirmed from Neo4j's APOC docs — https://neo4j.com/labs/apoc/4.1/export/gephi/ — and python-igraph's client — https://raw.githubusercontent.com/igraph/python-igraph/main/src/igraph/remote/gephi.py; the Gephi wiki page itself returned the repo README (**UNVERIFIED**).

**Staged transitions.** Heer & Robertson, InfoVis 2007 (https://idl.cs.washington.edu/files/2007-AnimatedTransitions-InfoVis.pdf): animation beat static in every transition (F(2,286) ≥ 22.03, p < .001); staging beat direct animation except when over-staged; "multiple stages with shorter durations provide more opportunities for losing targets"; about one second per stage. Bach, Pietriga & Fekete, GraphDiaries, TVCG 20(5), 2014 (https://aviz.fr/~bbach/graphdiaries/Bach2013GraphDiaries.pdf): remove (300 ms, red halos) → move (600 ms, slow-in/out) → add (300 ms, blue halos); add-first and parallel orderings rejected ("users cannot focus on a particular type of change"); a stability slider with **80% local optimisation as the default**; errors on "when is the group largest" 4% vs 18% for flipbook (p < .04). Crnovrsanin, Shilpika, Chandrasegaran & Ma, IEEE VIS 2020 (https://arxiv.org/abs/2009.02005), the only staging study on **online** streams found: deletion 450 → movement 600 → addition 450 → pause 500 ms; **batching by event count (or hybrid) beat batching by wall clock** on monitoring tasks (p < .05, p < .001) with no accuracy loss, and time-based batching scored significantly higher mental demand, frustration and effort (p < .01), 21 participants.

**3D.** Kotlarek et al., PacificVis 2020 (https://arxiv.org/abs/2001.06462), N = 20, Vive Pro vs monitor, same FM³ layout: path accuracy 3D 0.950 vs 2D 0.806 (p = .0065); **re-finding nodes 2D 0.951 vs 3D 0.923 (p < .0001), gap growing with graph size**; change detection no difference; 2D faster on everything; 85% preferred VR. No study of mental-map preservation for a *dynamic* layout in 3D was found (as of 2026-09-27).

### Judgment

Stability is for **orientation and tracking**, which is exactly what a person does in a live world: follow an entity, watch a cluster form, see a ghost shatter. It will not make counting or reading faster, and the literature says do not expect it to. So: anchor hard (the extremes beat the middle), with a scheduled refinement pass to repair the long edges that pure anchoring accumulates; cap per-tick velocity (DynNoSlice's force, portable to any tick loop: nothing teleports); place new entities at the centroid of their already-placed neighbours, never at d3's phyllotaxis default; batch deltas by event count and stage them remove → move → add at roughly 1.2–2 s total. A merge is remove-A, remove-B → move → add-AB with halos; a split is the reverse; both are already events in the log, so the client never has to infer them. Because spatial memory is measurably weaker in 3D (Kotlarek), the 3D explorer should hold positions harder than a 2D view would, and rely on persistent visible clusters rather than on the viewer remembering coordinates.

Keep layout out of the core. Positions are not part of the world; they are a client concern keyed by stable entity id (§7), persisted locally (IndexedDB) so a reload does not reshuffle a world the viewer has learned. The runner-up, a Rust layout as a deterministic projection of the log, becomes attractive only if sharing "this moment, this view" links is the demo's main gesture; then positions must be reproducible on another machine. Decide after the first prototype.

## 3. Time as a navigable dimension

### Facts

**Space-time cubes.** The generalised space-time cube framework (Bach, Dragicevic, Archambault, Hurter & Carpendale, CGF 2017, DOI 10.1111/cgf.12804, https://www.research.ed.ac.uk/en/publications/a-descriptive-framework-for-temporal-data-visualizations-based-on; EuroVis STAR 2014, https://diglib.eg.org/items/a32cc0c6-0f36-4acd-9aa4-3349e51de2cc) describes every temporal visualisation as operations on a conceptual cube (two data dimensions plus time): extraction (time cutting, space cutting, drilling), flattening (across time or space), geometry transformation, content transformation (aggregation, filtering, interpolation), juxtaposing, superimposing, or plain 3D rendering; dynamic networks are explicitly in scope. The catalogue at https://aviz.fr/~bbach/spacetimecubes/ tags 89 systems with 39 operations. Kristensson et al., TVCG 15(4), 2009 (https://arxiv.org/abs/0707.1618): for simple questions the 2D baseline had lower error; for complex questions needing "an overall grasp" the cube gave "on average twice as fast response times with no difference in error rates". Amini et al., TVCG 21(1), 2015 (abstract via PubMed 26357026): "advantages in 3D visualizations for more complex tasks", and "the 2D view relies significantly on 'scrubbing' the timeline, whereas the 3D view relies mainly on 3D camera navigation".

**Time as z for graphs (2.5D).** Dwyer & Eades 2002 "columns and worms" and Brandes & Corman 2003 "visual unrolling" stack per-time layers along z with nodes as columns (search snippets and https://www.researchgate.net/publication/4000924_Visual_Unrolling_of_Network_Evolution_and_the_Analysis_of_Dynamic_Discourse — **UNVERIFIED** beyond abstracts); GraphAEL (Erten et al., GD 2003, https://www2.cs.arizona.edu/~kobourov/graphael.pdf) animates evolving graphs in 2D and 3D with difference graphs between periods.

**World states as points.** van den Elzen, Holten, Blaas & van Wijk, "Reducing Snapshots to Points", TVCG 22(1), 2016 (abstract via https://research.tue.nl/en/publications/reducing-snapshots-to-points-a-visual-analytics-approach-to-dynam/): "We consider snapshots of the network as points in high-dimensional space and project these to two dimensions… users are enabled to detect stable states, recurring states, outlier topologies." Bach et al., "Time Curves", TVCG 2016 (https://aviz.fr/~bbach/timecurves/): fold a timeline so similar states sit close; demonstrated on Wikipedia revision histories, where edit wars appear as dense loops.

**Scrubbing and playback.** DimpVis (Kondo & Collins, TVCG 20(12), 2014, https://vialab.ca/research/dimpvis): drag a data item along its own hint path to move time; "subjectively preferred and quantitatively competitive with the traditional time slider, and significantly faster than small multiples". Robertson et al., TVCG 2008 (https://www.microsoft.com/en-us/research/publication/effectiveness-of-animation-in-trend-visualization/): "Animation is the fastest technique for presentation and participants find it enjoyable and exciting, it does lead to many participant errors… Animation is the least effective form for analysis; both static depictions of trends are significantly faster than animation, and the small multiples display is more accurate." Heer & Robertson (above): about one second per stage. Fluxicon Disco's token replay (https://fluxicon.com/book/read/mapview/): each token is one case moving "at the relative, actual speed of the corresponding case", with **standard** (calendar) versus **synchronized** (all cases start together) replay, a speed slider and a draggable progress marker; congestion groups tokens into larger bubbles. EventFlow (Monroe et al., TVCG 2013, https://www.cs.umd.edu/~ben/Monroe2013Temporal.pdf) gives the user simplification controls with a visual-complexity metric (2,700 elements cut to 492 in a case study). OCEL 2.0 (https://arxiv.org/pdf/2403.01975) has typed objects, qualified object-to-object relationships and attribute changes over time; its tools (OCπ, ocpa, Ocelot) are all 2D; **no 3D object-centric process-mining visualisation was found**.

**Branching futures.** Bank of England fan charts (1996; https://www.bankofengland.co.uk/-/media/boe/files/quarterly-bulletin/1998/the-inflation-report-projections-understanding-the-fan-chart): bands covering 10…90% of the forecast distribution, darker at the centre, fanning with horizon, chosen to avoid "spurious precision". Ensemble ("spaghetti") displays: Sanyal et al., Noodles, TVCG 16(6), 2010 (https://www.sci.utah.edu/~kpotter/Library/Papers/sanyal:2010:NTEU/index.html); Wang, Hazarika, Li & Shen's survey, TVCG 25(9), 2019 (PubMed 29994615) organises a decade of ensemble work by technique × task. **Sampled futures of a graph**: Schulz, Nocaj, Görtler, Deussen, Brandes & Weiskopf, "Probabilistic Graph Layout for Uncertain Network Visualization", TVCG 23(1), 2017 (https://graphics.uni-konstanz.de/publikationen/Schulz2017ProbabilisticGraphLayout/index.html): "a Monte Carlo process is used to decompose a probabilistic graph into its possible instances", each laid out, then node positions **splatted** into clouds and edges bundled; the "possible worlds" term is standard in uncertain-graph work (an uncertain graph with m independent edges "yields 2^m possible deterministic graphs" — https://www.vldb.org/pvldb/vol8/p2042-khan.pdf). Branching histories: VisTrails' version tree of provenance (https://www.vistrails.org/index.php/ProvenanceAnalytics). No evaluated visualisation of MCTS-style rollout trees surfaced. HN, 2026-02-08: "CineGraphs", probabilistic story graphs as branching interactive graphs, 101 points (https://hn.algolia.com/api/v1/search?query=%22graph%20visualization%22&tags=story&numericFilters=points%3E80,created_at_i%3E1756684800).

### Judgment

**Log offset is the time axis**, as the design page already draws it (`#0000`, "click the axis to scrub"), with a wall-clock mapping for humans. Design the explorer as a cube with a menu of operations rather than one fixed view: the default is a **time cut** (the world at offset o, in branch k); selecting an entity **flattens time** into its trail; comparing two moments is **juxtaposition** (small multiples), which the evidence says beats animation for answering questions; playback is for presentation and the demo, and it should stage changes (§2) and offer Disco's two clocks. DimpVis's gesture, dragging an entity along its own trajectory, is the natural 3D scrub because 3D users navigate with the camera, not the slider (Amini).

The map of worlds is a **time curve**: every world state, real or sampled, is a point; real history is one curve; each possible world is a branch off the tip, drawn dashed and fading with distance in probability; grading pulls a branch to the realised point or shatters it. This is the "git graph of worlds" already on the design page, given a geometry that a person can fly along. The 2.5D stack (time as z, entities as columns) is a useful secondary "entity timeline" view, not the default: it shows continuity of identity well and hides intra-layer structure.

## 4. Uncertainty in 3D

### Facts

**Sampled outcomes beat summaries for multi-entity judgments.** Hullman, Resnick & Adar, PLoS ONE 2015 (https://journals.plos.org/plosone/article?id=10.1371/journal.pone.0142444), N = 288: hypothetical outcome plots (HOPs, 400 ms per draw) gave mean absolute error ≈ 6–9 percentage points on "P(B > A)" tasks versus ≈ 36+ for error bars and violins (p < .001); on one-variable tasks HOPs were no better and worse for high-variance mean estimation; they require "visual stability across frames (e.g., by keeping the range of the y-axis fixed)". Kale, Nguyen, Kay & Hullman, TVCG 25(1), 2019 (abstract via Semantic Scholar, DOI 10.1109/TVCG.2018.2864909): HOPs let untrained observers infer trends at lower evidence than static ensembles. Kay et al., CHI 2016 (https://mucollective.northwestern.edu/project/when-ish-is-my-bus): quantile dotplots cut variance of probability estimates ~1.15× versus density plots. Fernandes et al., CHI 2018 (https://www.mjskay.com/papers/chi2018-uncertain-bus-decisions.pdf): incentivised decisions with 50-dot quantile dotplots reached 97% of optimal payoff (CI 95–98%), 5 points above a no-uncertainty control; dotplots and CDFs beat PDFs and intervals.

**Cones are misread; ensemble members steal attention.** Padilla, Ruginski & Creem-Regehr, Cognitive Research 2:40, 2017 (https://pmc.ncbi.nlm.nih.gov/articles/PMC5626802/): 70% of cone viewers thought the hurricane was growing versus 39% of ensemble viewers (N = 179); with an ensemble, a target lying **on** a drawn member was judged more affected even when farther from the centre 54.6–64.2% of the time — members "drew disproportionate attention despite lower proximity to storm center". Liu et al., TVCG 25(1), 2019 (PubMed 30136996, **snippet**): representative-sample ensembles "dispel misunderstandings that the size of the display represents the size of the storm".

**Visual variables.** MacEachren et al., TVCG 18(12), 2012, as ranked in Kinkeldey, MacEachren & Schiewe's review (Cartographic Journal 51(4), 2014, https://d-nb.info/1268428361/34): "Fuzziness ranked as the most intuitive of all signification methods, while transparency was above average (but with wide variation in reactions) and colour saturation was not judged as intuitive"; transparency was "among the best techniques for both data and uncertainty" in static 3D scenes. Boukhelifa et al., TVCG 2012 (abstract, DOI 10.1109/TVCG.2012.220): sketchiness "is as intuitive as blur; although people subjectively prefer dashing". Correll & Gleicher, TVCG 20(12), 2014 (https://graphics.cs.wisc.edu/Papers/2014/CG14/): gradient (transparency) and violin plots over bars with error bars. **Graph edges specifically**: Guo, Gomez, Ziemkiewicz & Laidlaw, TVCG 21(10), 2015 (DOI 10.1109/tvcg.2015.2424872, **snippet**): "fuzziness strongly interfered with the perception of an edge when paired with width". Schulz et al. 2017 (§3) is the closest prior art for "where might this entity be connected across sampled worlds"; no user-study numbers were retrieved.

**Animation caveats.** Heer & Robertson 2007: "Animation's ability to grab attention can be a powerful force for distraction"; stage so "only one action happens at a time". No study tests HOP-style sampling layered on a moving 3D camera (as of 2026-09-27).

### Judgment

The README's "dashed ghosts with probabilities" is the right idiom, and the evidence sharpens it: draw sampled futures as **members** (n of N worlds), not as a cone or a fan around an entity, because cones read as size; put a **frequency readout** next to every ghost ("7 of 20 futures") because members steal attention from the aggregate; encode probability with **opacity** (well supported, and cheap on the GPU) and mark hypothetical geometry with **dashing** (preferred by people, and already our visual language), not with fuzziness on edges, which interferes with width. Offer a HOP mode that cycles through sampled worlds one at a time, **only while the camera is still**; the one requirement the HOP authors state is frame stability, and a moving scene violates it. Scalar forecasts (edit count, degree over the next hour) belong in a 2D panel as quantile dotplots or fans, not in the scene. Per-entity position clouds across sampled worlds (Schulz) are a second-generation feature; the first slice needs ghosts and readouts.

## 5. The honest case against 3D, and where it wins

### Facts

**3D wins on topology tasks, with depth cues.** Ware & Franck, ACM TOG 15(2), 1996 (abstract via https://api.crossref.org/works/10.1145/234972.234975): on a path-tracing task, "head-coupled stereo viewing increased the size of an abstract graph that could be understood by a factor of three; stereo alone 1.6x; head coupling (motion) alone 2.2x". Ware & Mitchell, ACM TAP 5(1), 2008 (abstract at https://scholars.unh.edu/ccom/467/): with a very high resolution stereo display plus kinetic depth, unskilled observers traced paths in 333-node graphs at <10% error and skilled observers up to 1,000 nodes, "an order of magnitude increase over 2D display". Kotlarek et al. 2020 (§2): path accuracy 0.950 vs 0.806 in VR. Joos et al.'s 2025 survey of 138 immersive network papers (https://arxiv.org/html/2501.08500v2): stereo 3D helps community detection and path tracing, "2D remains faster for simpler graphs", "motion tracking outperforms static stereoscopy", and immersion "incur[s] steeper learning curves". Yang et al., TVCG 25(1), 2019 (https://arxiv.org/abs/1908.02089): "Careful use of the third spatial dimension can resolve visual clutter" for flow maps whose data is spherical.

**2D wins on speed, memory, overview and text.** Cockburn & McKenzie, CHI 2001 (https://www.csse.canterbury.ac.nz/andrew.cockburn/papers/chi01DM.pdf): 2D vs perspective-3D document mountain; storing 437 s vs 506 s (n.s.), retrieval 5.98 s vs 6.77 s (n.s.), 3D slower at every density, **yet subjects significantly preferred 3D**. CHI 2002 (https://www.csse.canterbury.ac.nz/andrew.cockburn/papers/chi02DM.pdf), N = 69: "performance deteriorated in both the physical and virtual systems as their freedom to locate items in the third dimension increased"; 2D rated significantly less cluttered. Kotlarek 2020: 2D better at re-finding nodes and faster on every task. Kraus et al., CHI 2020 (https://kops.uni-konstanz.de/bitstream/123456789/49555/1/Kraus_2-1x6gz2rwuh45i0.pdf), N = 48: 3D better on single-value lookup, but on overview tasks "required significantly more time… performed worse… in terms of error rate", blamed on "perspective distortion, overlapping, and occlusion". Bach et al., TVCG 24(1), 2018 (**snippet**): "the desktop environment is still fastest and most precise in almost all cases". Feyer et al., TVCG 30(1), 2024 (https://arxiv.org/abs/2307.10674): 2D vs 2.5D vs 3D multilayer networks in VR, "no clear overall winner".

**Why.** Munzner, "Process and Pitfalls", 2008 (https://www.cs.ubc.ca/labs/imager/tr/2008/pitfalls/pitfalls.pdf): "The most serious problem with a 3D layout is occlusion. The ability to interactively change the point of view with navigational controls does not solve the problem. Because of the limitations of human memory, comparing something visible with memories of what was seen before is more difficult than comparing things simultaneously visible side by side… In many cases, [multiple linked 2D] views are more effective than simply jumping to 3D… users have difficulty in making precise length judgements because of perspective foreshortening, and also that text is difficult to read unless it is billboarded to a 2D plane." Her book's rule "No unjustified 3D" (VAD ch. 6 §6.3; chapter text not online, **snippet**; further reading page https://www.cs.ubc.ca/~tmm/vadbook/). Shneiderman, IEEE CG&A 23(6), 2003 (https://www.cs.umd.edu/~ben/papers/Shneiderman2003Why.pdf): "disorienting navigation, complex user actions, and annoying occlusions can slow performance"; his checklist for enhanced 3D: minimise navigation steps, "keep text readable (… no more than 30-degree tilt)", "provide overviews… (plan view display, aggregated views)", "allow teleportation (rapid context shifts by selecting destination in an overview)".

**Mitigations with evidence.** Drogemuller et al., BDVA 2018 (https://wearables.unisa.edu.au/uploads/1/2/7/6/127656642/evaluating-navigation-techniques.pdf): flying beat teleportation for search; a **worlds-in-miniature overview** was least demanding and preferred for overview tasks; edges drawn at alpha 0.2 "to reduce occlusion issues". Sorger et al., AIVR 2019 (https://arxiv.org/abs/1910.06825): overview + immersive detail for large dynamic networks. An animated 2D → 3D transition let people re-find a cluster in 9.6–13.5 s versus 28.8 s for an instant spawn (Frontiers VR 2023, https://www.frontiersin.org/journals/virtual-reality/articles/10.3389/frvir.2023.1155628/full). Munzner's H3 (1997, https://graphics.stanford.edu/papers/h3/html/) laid out >20,000-node hierarchies in hyperbolic 3D with focus+context, but assumes a spanning tree and reports no user study. Fisheye/focus+context (Furnas; Sarkar & Brown), fog as a depth cue and 3D edge bundling: design-text advice only, **UNVERIFIED** by a controlled comparison in this session.

**What HN rewarded** (points from the Algolia API, 2026-09-27): anvaka's Software Galaxies 747 pts (https://hn.algolia.com/api/v1/search?query=%22software%20galaxies%22&tags=story), Map of GitHub 717 and 471 (deliberately a 2D map with place names), GitHub globe 376 (three.js, InstancedMesh, hover shows a real PR — https://github.blog/2020-12-21-how-we-built-the-github-globe/), Stripe globe 192 (https://stripe.com/blog/globe), earth.nullschool.net 438 with the **URL encoding time and view** (https://earth.nullschool.net/about.html), Windy 1,052, Flightradar24 874 (live + replay + one entity's trail), Gource 256 (an event log as a living world; unreadable on large repos), Listen to Wikipedia 140/134 and reposted ~20 times (https://listen.hatnote.com/); the Wikipedia recent-changes map was **archived in Nov 2025** because temporary accounts removed IPs (https://rcmap.hatnote.com/). In the last twelve months no "3d graph", "force graph" or "knowledge graph 3d" story passed 100 points; the 3D front-page hits were particle and physics sims (Strange Attractors 804, https://blog.shashanktomar.com/posts/strange-attractors; a three-body simulator 249 with state in the URL). Pattern across winners: recognisable data, continuous motion with the camera as the only control, a shareable URL for a moment and viewpoint, hover revealing a concrete record, and a technical write-up that earns a second post.

### Judgment

The honest reading: **every measured 3D win for abstract graphs came with motion or stereo, on structure tasks**; perspective 3D on a flat monitor is the least supported condition, and people prefer it while performing no better. The honest reading also says the demo value is real and Dave's instinct is right about what makes a world *explorable*: the winners were all fly-through, live, and searchable. The reconciliation is a division of labour. **3D is the explorer**: it is where a person moves through a world, watches it form, follows an entity, and flies into a possible future. **2D panels are the readers**: the evidence table, an entity's timeline, a forecast's record and the calibration chart live beside the scene, linked by selection, because comparing side by side beats comparing against memory. Constraints that keep 3D a strength, each traceable to a study above: keep the scene in gentle continuous rotation when idle and make rotation the default drag (kinetic depth is the cue that made the Ware results); a miniature 2D overview (Drogemuller); search-to-fly and camera presets (Shneiderman's teleportation); billboarded labels, none beyond ~30° tilt; edges at low alpha or bundled; level of detail (zoomed out, types and counts; zoomed in, entities); a 2D orthographic "flatten" toggle for the person who needs to read rather than explore. Before launch, run a small task study on our own world (find X; what changed since o; is X connected to Y) in 2D and 3D and publish the numbers with the demo; "we measured it" is itself a Show HN story.

## 7. What the gate-2 query API should expose now

### Facts

The README fixes the principle: "The view reads the world through the same query interface as MCP, so the renderer can change without touching the core." The design page fixes offsets as the scrub axis and "Level of detail, always". Repairs (aliases, links, type mappings) are already "events of their own, with a confidence and a source… any repair can be revoked". Browser `EventSource` resends `Last-Event-ID` on reconnect and honours `retry:` (MDN, cited in 0003 §6); axum's `Event` carries `id`, `event`, `data` — https://docs.rs/axum/latest/axum/response/sse/index.html. Wikimedia's own stream resumes from `Last-Event-ID` and keeps "between 7 and 31 days of history" — https://wikitech.wikimedia.org/wiki/Event_Platform/EventStreams. Every candidate client library consumes the d3 shape (`{nodes:[{id}], links:[{source,target}]}`); cosmos.gl consumes positional arrays by **index** with `NaN` for absent points (§1), so a client that adopts it must keep its own stable id → index allocator. The Gephi streaming format is the closest existing precedent for graph deltas (`an/cn/dn/ae/ce/de`, one object per line) (§2). Crnovrsanin 2020 (§2): batch deltas for display by event count, not wall clock.

### Judgment

Expose these in gate 2, as the same handlers that back MCP:

1. **Snapshot at a point.** `GET /world?at=<offset>&branch=<world_id>&lod=<level>&focus=<entity_id>&hops=<n>` → `{offset, ts, branch, entities[], relationships[], aggregates[]}`. `at` is a log offset (a `ts` alternative resolves through a time index); `branch` defaults to `actual`; `lod` is `type` (per-type counts and top-N entities), `cluster` (community nodes with member counts), or `entity` (full); `focus` + `hops` returns an ego-network. Zoomed out asks for `lod=type`; zoomed in asks for entities near a focus. Without `lod` the API cannot serve a world of the measured size (§0).
2. **Deltas over SSE.** `GET /events?since=<offset>&branch=<world_id>&lod=<level>`, each event with `id: <offset>` so `Last-Event-ID` resumes exactly, and typed `event:` names: `entity.add|change|remove`, `rel.add|change|remove`, `entity.merge {survivor, absorbed[]}`, `entity.split {source, parts[]}`, `forecast.issued|graded`, `branch.opened|pruned`, `tick {offset, ts}`. The client batches by event count for staging. Deltas at coarse `lod` are aggregate changes (counts), so the zoomed-out view stays live without receiving every entity.
3. **Stable entity ids.** An id is assigned at first sight and never reused; a merge emits `entity.merge` and an alias, never a fresh id for the survivor; a revoked repair emits `entity.split`. This is a `s2w-model` invariant, and it is what lets a client keep positions across reloads and across the 2D → 3D swap.
4. **Branches.** `GET /branches?at=<offset>` lists open possible worlds: `{world_id, parent, fork_offset, horizon, weight, forecast_ids[]}`; `GET /world?branch=k&at=o` is the same snapshot call inside a sampled future; `GET /diff?from=actual@o&to=k@o'` returns the entity/relationship differences so ghosts are computed once, server-side. A branch's forecast record is one link away, as the design page requires.
5. **Trails and time index.** `GET /entity/:id/history?from=<offset>&to=<offset>` (the space-time "flatten"); `GET /time?ts=<iso>` ↔ offset; `GET /entity/:id/forecasts` (the `forecast.ask` shape with track records).
6. **Shareable moment.** Everything a view needs to reproduce itself is in the query string (`at`, `branch`, `focus`, `lod`); the explorer appends camera pose client-side. This is nullschool's trick and it costs nothing now.
7. **Payload shape.** JSON in gate 2 with the d3 field names; a columnar `application/octet-stream` variant of the snapshot for the 3D explorer later, without changing semantics.

Nothing above names a renderer, a layout, or three.js, which is the point.

## Recommended stack

**First choice.** three.js 0.186 used directly: one `InstancedMesh` for entities, one `LineSegments2` for relationships, sprite or SDF labels billboarded with priority-based density; client-side incremental layout (d3-force-3d or an own loop) with anchoring, a velocity cap, centroid placement of new nodes and staged remove → move → add batches; positions keyed by stable entity id and persisted in IndexedDB; the page served as a prebuilt ESM bundle embedded by memory-serve; 2D linked panels in plain DOM; the gate-2 2D graph on `force-graph` or `sigma` with the same client data contract. Measure the frame budget in-repo on the Wikipedia stream at each `lod`.

**Runner-up.** 3d-force-graph for the first prototype, because the 2D twin shares its contract and the demo can exist in a day; replace it when the visible set passes a few thousand objects.

**What would flip it.** A maintained GPU 3D force layout (the only one today, @jonobr1/force-directed-graph, has 95 stars); cosmos.gl growing a z-axis, which its charter does not promise; deck.gl's graph layers gaining a maintainer and 3D, which would matter if the world becomes a point cloud of 10^5–10^6 entities with few visible edges; or the pre-launch task study showing 3D losing on every task we care about, in which case 2.5D layered becomes the explorer and 3D the demo mode.

## Sketch of the explorer's core interactions

- **Idle**: the world turns slowly; new entities fade in at their neighbours' centroid; merges and splits play as staged halos; a ticker shows the offset and wall clock.
- **Drag** rotates; **scroll** dollies; **double-click** an entity to fly to it (search-to-fly from a box that also accepts an offset or a timestamp); **camera presets**: overview, focus, flatten (orthographic 2D), timeline (2.5D stack).
- **Miniature overview** in a corner (2D projection of the scene with the camera frustum); click to teleport.
- **Scrub**: a log-offset axis with wall-clock labels; drag the axis, or grab a selected entity and drag it along its own trail (DimpVis); playback with two clocks and staged transitions; small multiples on request for "compare o₁ and o₂".
- **Select** an entity: its trail appears in the scene; the 2D panels show its evidence, relationships, open forecasts with track records; ghosts of its sampled futures appear dashed with "n of N" readouts; a HOP toggle cycles sampled worlds while the camera is still.
- **Map of worlds**: a time curve of world states; real history solid, branches dashed and fading with probability; click a branch to enter that possible world; graded branches snap to the realised point or shatter.
- **Level of detail**: types and counts far away, clusters in the middle distance, entities near the focus; the query `lod` follows the camera distance.
- **Share**: the URL encodes offset, branch, focus, lod and camera pose.

## Design implications

Dispositioned by karpathy, 2026-09-27. Most land in the issue that builds them.

1. **#10 query API**: snapshot at offset with `branch` and `lod`, SSE deltas with `id: <offset>` and typed events including merge/split, `/branches`, `/diff`, `/entity/:id/history`, `/time`; JSON in the d3 field shape. → deferred: stream2worlds#10
2. **`s2w-model` invariant**: entity ids are assigned once and never reused; merges alias, revoked repairs split; no id changes on either. → deferred: stream2worlds#9 (the fold owns identity; also gate 3 merge semantics)
3. **Level of detail is an API parameter** (`lod=type|cluster|entity`, `focus`+`hops`), required by the measured stream size, not a rendering option. → deferred: stream2worlds#10
4. **Layout stays out of the core**; positions are client-owned, keyed by entity id, persisted locally; a Rust-side layout is reconsidered only if shareable moments need reproducible positions. → adopted: stream2worlds#21 constraint (2026-09-27)
5. **Time is the log offset** in every view and URL, with a timestamp index; the explorer's URL encodes offset, branch, focus, lod and camera. → deferred: stream2worlds#10
6. **README dashboard row and #21**: name three.js used directly (instanced nodes, fat-line edges) as the explorer's first choice and 3d-force-graph as the prototype path; add the constraints that keep 3D a strength (continuous rotation, miniature overview, search-to-fly, billboarded labels, low-alpha edges, 2D linked panels, flatten toggle). → adopted: README technical-architecture Dashboard row and stream2worlds#21 (2026-09-27)
7. **#21 finish line**: add a pre-launch task study (find X; what changed since o; is X connected to Y) in 2D and 3D on the Wikipedia world, numbers published with the demo. → adopted: stream2worlds#21 finish line (2026-09-27)
8. **Uncertainty rendering rule** for the possible-worlds view: ensemble members with "n of N" readouts, dashed ghosts with opacity ∝ frequency, no cones in the scene, HOP mode only with a still camera; scalar forecasts as quantile dotplots or fans in a 2D panel. The planned "Showing uncertainty" note narrows to what this does not cover (position clouds, calibration display). → deferred: stream2worlds#21; the planned "Showing uncertainty" note narrowed (research/README.md)
9. **Staged, count-batched deltas** in the view (remove → move → add, ~1.2–2 s; batch by event count or hybrid), and new-entity placement at neighbours' centroid. → deferred: stream2worlds#21
10. **Delivery**: committed prebuilt bundle embedded by memory-serve; Node only in the CI job that regenerates it; a check that the bundle matches the lockfile. → deferred: stream2worlds#10 (the 2D view ships the first bundle)
